# Профиль SystemC-модели

Модель выполняет FC-слои: `Y = sigmoid(X * W_eigen + b)`.
Обычные веса имеют форму `[K,N]`, X — `[M,K]`, Y — `[M,N]`.
Обучение остаётся в исходной Eigen-реализации. Эксперименты используют
синтетические входы и Xavier-веса с seed=42, без обучения.
Bias повторяется по выходам: -0.2, -0.1, 0, 0.1, 0.2.
После симуляции `main` сверяет все выходы с обычным расчётом на CPU
через точную sigmoid. Допуск — `1e-4`, поскольку модель использует LUT.
Ошибка или незавершённая команда приводят к ненулевому коду возврата.

## Реализованная архитектура

`Accelerator` объединяет внешнюю RAM, DMA, Input/Weight SRAM,
массив PE с ACC, reduction, bias, ROM sigmoid LUT, Output SRAM,
scheduler и FIFO на 16 команд. Аппаратные компоненты — модули SystemC.
Схемы исходного проекта находятся в [описании архитектуры](../architecture/README.md).

CPU-поток подаёт команды; поток FIFO выполняет их последовательно.
Scheduler получает блоки через DMA, вызывает вычисления PE и записывает
выход в RAM. MAC, reduction и интерполяция LUT выполняются без задержки;
отдельные потоки MAC не создаются. Обмены внутри scheduler последовательны.
SRAM использует single buffering; double buffering аппаратного проекта пока не реализован.

## Данные и конфигурация

`AcceleratorConfig` задаёт число PE, microbatch, output tile и K tile
до создания модулей. В экспериментах размеры tiles — 8/4/64,
число PE — 1, 2, 4 или 8. Во время расчёта конфигурация не меняется.

FC-команда содержит M/N/K и byte addresses X, packed W, bias и Y.
Логический descriptor — 64 байта, FIFO — 1024 байта.
Бинарная сериализация descriptor и регистры управления не моделируются.
Данные — FP32, блоки RAM выровнены на 16 байт.
X/Y хранятся row-major, bias — `[N]`. Веса имеют layout
`Wpacked[n_tile][k_tile][pe][local_k][lane]`.
В каждом K tile вход k назначается PE `k % pe_count`,
локальный индекс — `k / pe_count`; lane обозначает выход в N tile.
Локальная ёмкость K — `ceil(K_tile / pe_count)`, padding заполнен нулями.
Распределение k начинается заново в каждом K tile.

`load_mlp()` размещает веса/bias всех слоёв и два activation buffers
по `M × max(widths)` значений. Команды чередуют адреса X/Y;
следующий слой использует Y предыдущего. Глубина сети не меняет аппаратуру.
Начальная запись RAM и чтение результата CPU после `sc_start()`
не входят в профиль коммуникаций.

Веса PyTorch загружаются через `python/scripts/export_pytorch.py`.
Он читает `.pt/.pth`, сохранённый через `torch.save(model.state_dict(), path)`,
либо checkpoint с ключом `state_dict` или `model_state_dict`.
Поддерживаются FC layers Linear, в том числе без bias.
Сеть должна применять sigmoid после каждого слоя, включая последний:
файл весов не содержит сведения об activation.
По умолчанию слои читаются в порядке ключей state_dict; если порядок
регистрации отличается от forward, его задают через `--layers fc1 fc2 ...`.

Текстовый формат начинается с `MLP_WEIGHTS_V1` и числа слоёв.
Каждый слой содержит K/N, затем K×N весов row-major и N bias.
Экспорт транспонирует PyTorch-веса `[N,K]` в формат модели `[K,N]`.
FP32 записывается с девятью значащими цифрами.
Команда `--weights model.txt PE batch` определяет размеры сети из файла
и использует обычный weight packing, DMA и FC command queue.
Загрузка файла до симуляции не добавляет model time.

Для реальных входов exporter принимает `--input input.pt`, где input.pt
содержит сохранённый тензор `[M,K]`. Рядом создаётся `model.input.txt`:
заголовок `MLP_INPUT_V1 M K` и M×K значений row-major.
Симулятор читает его через `--input model.input.txt`; batch берётся из файла.
Нормализацию изображений выполняет пользователь так же, как при обучении.
Без входного файла используется синтетический batch с seed=42.

Загрузка проверена сравнением с PyTorch: для сети 784→512→256→128→10
на batch=8 максимальное расхождение составило около `2.4e-6`.
Также проверены обученные веса небольшой сети, слои без bias,
оба формата checkpoint, явный порядок слоёв и сеть из 20 слоёв.

LUT содержит 2049 FP32-узлов на [-16,16] с шагом 1/64.
Таблица создаётся один раз; внутри интервала применяется линейная
интерполяция, снаружи результат насыщается к 0 или 1.

## Расчёт одного слоя

1. Разбить M на microbatch и N на output tiles
2. Очистить ACC всех PE для текущей пары и загрузить bias tile
3. Для каждого K tile прочитать строки X, распределить входы через DMA
   и загрузить полные packed-блоки весов активных PE
4. Выполнить MAC для действительных M/K/N, сохраняя ACC между K tiles
5. Получить ACC от всех PE и сложить их деревом reduction
6. Прибавить bias, применить LUT, передать действительные выходы в Output SRAM
7. Через DMA записать строки tile в row-major Y

Загрузка Weight SRAM включает padding. Передача SRAM → PE пропускает
лишние K-строки, но сохраняет полную ширину lane; MAC пропускают лишние N.
PE без входов пропускает загрузку, но участвует в итоговом reduction:
его ACC может содержать результат предыдущих K tiles.
Входы загружаются заново для каждого N tile, веса — для каждого microbatch.

## Метрики

`Transactions::transfer()` ждёт 1 ns SystemC и увеличивает счётчики
типа, сообщений и переданных байт. Одна единица model time соответствует
этому ожиданию. 1 ns — масштаб ядра SystemC, а не физическая задержка FPGA.
Подача следующей команды CPU перекрывается с обработкой предыдущей,
поэтому model time и суммарное число сообщений различаются.
Объём сообщения не меняет длительность передачи.

Для пары microbatch/N tile число сообщений данных равно
`P + 5 + 2*Mv + sum_k(Mv + 5*Pk)`, где P — число PE,
Mv — действительный microbatch, Pk — число активных PE текущего K tile.
Учтены bias, reduction, LUT/output, построчная выгрузка Y и обмены X/весов.
FIFO добавляет два сообщения на FC-команду.

Один `acc += x*w` — один полезный MAC. Каждый K tile добавляет каждому PE
`8 × ceil(64/P) × 4` доступных позиций MAC. Utilization — отношение полезных MAC
к этим позициям за весь запуск. Она учитывает хвосты M/K/N и неактивные PE.
Это заполнение tiles, а не занятость по времени: арифметика занимает нулевое время.

Память — выделенная ёмкость RAM, SRAM, ACC, bias, ROM и FIFO.
RAM включает padding, выравнивание и оба activation buffers.
Временные векторы C++, исходные Eigen-матрицы и служебные объекты SystemC
не учитываются; итог не является RSS процесса.

## Изменение числа PE

Сеть 784→128→10, batch=8; входы и веса одинаковы во всех запусках.

| PE | Model time | Transactions | Всего памяти, байт | MAC каждого PE | Utilization каждого PE |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 6259 | 6260 | 495420 | 813056 | 94.08% |
| 2 | 8404 | 8405 | 495548 | 406528 | 94.08% |
| 4 | 12694 | 12695 | 495804 | 203264 | 94.08% |
| 8 | 21274 | 21275 | 496316 | 101632 | 94.08% |

Полезная работа сети остаётся 813056 MAC. С ростом PE меньше работы у каждого,
но больше сообщений между DMA, локальными SRAM и PE, а также PE → reduction.
Последовательная обработка этих сообщений увеличивает model time.
Временного выигрыша от параллельных MAC здесь нет: они выполняются без задержки.
Эти результаты характеризуют коммуникации, а не производительность физической FPGA.

RAM и суммарные Input/Weight SRAM одинаковы для P=1/2/4/8, поскольку 64
делится на эти P. Растёт ACC — по 128 байт на PE. Если P не делит 64,
дополнительный packed padding может увеличить также RAM и SRAM.

## Воспроизведение

```powershell
$env:PATH = "$env:LOCALAPPDATA\mlp_cpp\mingw64\bin;$env:PATH"
cmake --build build --config Release -j 2
python experiments/run.py
```

GCC 16.2, SystemC 3.0.2, C++17, Release. Модель запущена после сборки;
все шесть запусков прошли сравнение с CPU в `main`.
Отдельных тестов нет. Дополнительно через `main` проверены неполные
M/N/K tiles, PE=3 и PE=5, PE без входов и сеть из 20 слоёв
при FIFO на 16 команд. Итоговые данные:

- [Общая таблица](summary.csv)
- [Память по блокам](memory.csv)
- [Каждый PE](pe.csv)
- [Передачи по типам](transactions.csv)

Промежуточные JSON новых запусков сохраняются в игнорируемом
`experiments/results/`. CSV здесь фиксируют опубликованный набор результатов.
Обучение для лабораторной работы №3 не требуется. При необходимости
можно загрузить заранее обученные параметры PyTorch через exporter.
